# sqllab

インデックスなしでクエリを実行してテーブルスキャンを体感し、推奨インデックスを
追加して同じクエリを再実行すると、実行計画がインデックスサーチに切り替わる様子を
その場で確認できるインタラクティブなクエリ最適化サンドボックスです。訪問者ごとに
独立した一時的なSQLiteデータベースが割り当てられるため、あなたの操作は他の誰にも
影響せず、セッションがアイドルになれば何も残りません。

もう一つのパネルでは、平易な英語の質問を[WebLLM](https://github.com/mlc-ai/web-llm)
（WebGPU）を使って**ブラウザ内だけで**SQLに変換します——サーバー側のモデルも
APIキーも不要で、データはどこにも送信されません。

```
sqllab/
├── internal/db/         スキーマ・決定論的データセット生成・すべてのクエリ（手入力もAI生成も）が通過するガード
├── internal/session/     訪問者ごとの一時的なインメモリDB + 追い出し処理
├── internal/scenarios/   4つの定番「遅いクエリ／修正」ペア
├── internal/api/         HTTPハンドラ
├── web/                  埋め込みフロントエンド（ビルド不要）
└── cmd/server/           エントリポイント：起動時に一度だけデータセットを生成し、1ポートで全てを配信
```

## なぜこのプロジェクトを作ったか

職務経歴の「負荷プロファイリングとMySQLインデックス最適化によりダッシュボード
応答時間を40%改善」（ゼロボード）という一文は事実ですが、紙の上の一文のままでは
検証しようがありません。このプロジェクトは、その裏側にあるメカニズムを訪問者
自身の手で再現できる形にしました：現実的な遅いクエリを選び、`EXPLAIN QUERY PLAN`
がフルテーブルスキャンと数百ミリ秒単位の実測時間を示すのを見て、それを解消する
まさにそのインデックスを追加し、再実行して、実行計画と実測時間の両方が変わる
様子を見る——主張の言い換えではなく、再現可能な証明です。

AIパネルを追加したのは、生成AIの実務経験も別の軸として示す価値があると考えた
ためです。そしてこれが興味深い制約を生みました：公開デモがサーバー側で従量課金
のLLM APIを呼び出すのは安全ではありません（詳細は下記「設計判断」）——そのため、
自然言語→SQL変換機能は、誰が何回クリックしても課金が発生しない場所で動かす
必要がありました。

## ライブデモ

[Render](https://render.com)の無料プランに`render.yaml`経由でデプロイ——
Docker不要、無料プランはクレジットカード登録も不要です。このリポジトリを
接続すればRenderが`cmd/server`を自動ビルドします。無料プランは15分間
アクセスがないとスリープするため、スリープ後の最初のリクエストはウェイク
アップに数秒かかります。

```bash
go run ./cmd/server
# http://localhost:8080 を開く
```

## 設計判断・トレードオフ

**AI機能をブラウザ内だけで完結させた理由。** 公開デモがリクエストのたびに
従量課金LLM API（Claude、OpenAI）を呼び出すと、実際のAPIキーが無制限の悪用に
晒されるか、それでもなお課金リスクの残る利用上限の仕組みが必要になります。
訪問者自身のブラウザでWebGPU経由の小型モデル（`Qwen2.5-1.5B-Instruct`。
このリストは変わりうるため、ハードコードせずWebLLMのモデルレジストリから
動的に解決）を実行すれば、この問題を根本から回避できます：サーバーは質問の
内容を一切見ず、有料APIも呼ばず、推論コストはこのプロジェクトのホスティング
費用ではなく訪問者自身のGPUが負担します。トレードオフも正直に書いておくと、
1.5BパラメータのモデルはSQL生成においてClaudeより明らかに弱く、WebGPUは
全てのブラウザで使えるわけではありません（Safari、多くのモバイルブラウザ）
——パネルは`navigator.gpu`をフィーチャー検出し、使えない場合は説明付きで
無効化されます（黙って失敗することはありません）。コアのクエリ・インデックス
デモ自体はAIなしでも完全に機能します。

**AI生成SQLを手入力SQLより信頼しない。** モデルが出力した内容は同じ
`/api/query`エンドポイントに送信され、訪問者が手で入力したものと全く同じ
`internal/db/guard.go`の検証を通過します——`SELECT` / `EXPLAIN QUERY PLAN` /
`CREATE INDEX` / `DROP INDEX`のみを許可するアローリスト、単一ステートメント
の強制、インデックスDDL向けのテーブル・カラムのホワイトリスト、多層防御
としての`ATTACH`/`PRAGMA`ブロックリスト、3秒の実行タイムアウト。SQL文字列の
出所は、それが安全に実行できるかどうかを何も保証しません。

**共有データセットではなく訪問者ごとの分離。** 各セッションは独自の
`:memory:` SQLiteデータベースを持ち、共有の読み取り専用テンプレートファイルを
`ATTACH`してテーブルを一括コピーすることで生成されます（100ミリ秒未満）。
訪問者ごとに約20万行を再生成するのではないので高速です。これにより、ある
訪問者が追加・削除したインデックスが他の誰のデモにも漏れ出すことはなく、
壊れうる共有可変状態も存在しません。アイドルセッションは10分で追い出され、
上限（同時20セッション）が無料プランの512MB RAM予算を保護します——
`internal/session/store.go`参照。

**データセットのサイズは意図的に控えめ。** `orders`（5万行）と`order_items`
（15万行）は、約20の同時インメモリコピーが512MBに余裕を持って収まる
サイズです。このスケールでインデックスなしのスキャンが体感的に遅くなる
主な要因は、行数そのものよりもRenderの無料プランのスロットリングされた
CPU（0.1 vCPU）です。UI上のコピーで正確なミリ秒数を約束していないのも
そのためで、共有CPUの性能はばらつくため、相対的なビフォー・アフターを
示す方が誠実な見せ方だと判断しました。

**元の実績がMySQL固有の話であってもSQLiteを選んだ理由。** このプロジェクトが
再現している職務経歴の一文は文字通りMySQLのインデックス最適化についての
ものであり、MySQLの`EXPLAIN`／`EXPLAIN ANALYZE`（8.0.18以降）はSQLiteの
`EXPLAIN QUERY PLAN`より実際に多くの情報を示します：ステップごとの実測行数
と実測時間、`key_len`（複合インデックスの何列目まで実際に使われたか）、
`filtered`の推定割合、そして`Extra`列（`Using filesort`、
`Using temporary`、`Using index condition`）——これらにSQlite側の対応物は
ありません。このギャップは本物であり、隠さずそのまま残しています——
これを埋めるには、この節がここまで前提にしてきた性質（無料のWebサービスが
訪問者ごとに100ミリ秒未満でDBを生成・破棄できる、埋め込み型・単一プロセスの
データベースであること）を手放す必要があるからです。MySQLのクライアント
サーバー型モデルは、どんな価格帯でもその性質を持ちません（上記のライブ
デモのホスティング制約を参照）。一方で、メカニズムそのもの——複合インデックス
の欠如がスキャンをサーチに変える、という修正とその理屈——はInnoDBでも
そのまま成り立ちます。

## テストの実行

```bash
go test ./... -v
```

`internal/db/guard_test.go`はステートメントのアローリスト・ブロックリスト
（スタックされた複数ステートメントや`ATTACH`のようなAI的な入力の拒否を含む）
をカバーし、`internal/session/store_test.go`はセッション生成・上限制御・
アイドル追い出しをカバー、`internal/scenarios`は全ての定番シナリオの
クエリと推奨インデックスが実際にガードを通過することを検証（シナリオの
タイプミスがデモを静かに壊す前にCIで検知）、`internal/api/handlers_test.go`
は`httptest`で最初のリクエストでのセッション自動発行を含むHTTPフロー
全体を検証しています。

## 既知の制限・今後の展望

- **サーバー側LLMプロバイダは未実装。** 関連プロジェクトのecocopilotで
  確立した`LLM_PROVIDER=ollama|claude|openai`という切り替え可能な
  パターンをここにも取り入れれば（デフォルトはオフ、自分のAPIキーで
  ローカル実行する場合のみ環境変数でオプトイン）、無料のブラウザ内
  モデルとClaudeのSQL生成品質を訪問者が比較できるようになります。
  WebLLM方式で回避したはずのコスト・悪用リスクを公開デモに再導入
  しないよう、意図的に対象外としています。
- **インメモリセッションはプロセス再起動で消える。** デモとしては
  許容範囲（Renderの無料プランはどのみちアイドル時にスリープする）
  ですが、実プロダクトであれば永続化が必要になります——それは
  このプロジェクトの主眼ではありません。
- **AIパネルにはWebGPUが必須。** WebGPU非対応ブラウザ（主にSafariや
  モバイル）向けのCPUのみで動く小型モデルへのフォールバックは
  まだありません。

## 各パッケージが示すもの

| パッケージ | 示すもの |
|---|---|
| `internal/db` | インデックスが実行計画を変える「理由」の理解——決定論的データセット生成、`EXPLAIN QUERY PLAN`のパース、セキュリティを意識したステートメント検証 |
| `internal/session` | メモリ制約のあるホスト上でのリソース制限付きマルチテナント分離：上限制御、アイドル追い出し、共有可変状態の排除 |
| `web/app.js` | クライアント側LLM連携（WebLLM/WebGPU）とグレースフルなフィーチャー検出——サーバー側のコスト・セキュリティリスクを伴わない生成AI活用経験 |
| `internal/api` | 人間由来かAI生成かを問わず、あらゆる入力を等しく信頼しない公開HTTP API |
